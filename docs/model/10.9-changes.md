# Model 10.9: what changed from 10.8

`EcoCommute_10.9_web_flow.xml` is the 10.8 export plus the elements the web flow needs. Nothing in 10.8 was changed or removed (`tests/test_model_10_9.py` checks this). The file is generated by [scripts/build_model_10_9.py](scripts/build_model_10_9.py) and was imported twice (see "Intelligence on import"); the corrected file passes Intelligence with no errors. Every new requirement is a Draft with all quality flags false, so Intelligence (or the team) has to set them.

Regenerate with `python -I docs/model/scripts/build_model_10_9.py`.

## Numbering

The model's own scheme was kept, and new elements take the next free number in the group they belong to:

| Kind | Scheme | New numbers |
|---|---|---|
| Needs (Statement) | 1.x.x under a stakeholder group | 1.1.9, 1.1.10, 1.1.11 (Commuters), 1.2.4 (Pilot Administrator) |
| Stakeholder requirements | 2.x.x under the same group | 2.1.11-2.1.14, 2.2.5 |
| System requirements | 3.1 input/output, 3.2 interfaces, 3.3 functional, 3.4 system-wide | 3.1.1.8-3.1.1.10, 3.1.2.5-3.1.2.7, 3.2.9, 3.2.10, 3.3.1.9-3.3.1.12, 3.4.5.4, 3.4.6.2 |
| External system | X.n | X.6 Route Service |
| Use case | UC.n with UC.n.m steps | UC.3 with UC.3.1-UC.3.11 |
| Risks | TR.n | TR.10-TR.12 |

Input/output and conduit elements are unnumbered, as the UC.1 ones are.

## What was added

**Needs.** 1.1.9 Compare every way before I choose; 1.1.10 Enjoy steady green choices; 1.1.11 See what we achieve together; 1.2.4 Encourage campus-wide participation. Need 1.1.5 (Track my progress) already existed and is reused.

**Stakeholder requirements** (full text in [SPEC.md](../../SPEC.md)): 2.1.11 compare travel modes between two places; 2.1.12 count only trips the Commuter confirms; 2.1.13 award badges by published rules; 2.1.14 ignore repeated and excess trips; 2.2.5 show shared campus progress. The existing 2.1.4 and 2.1.5 are also satisfied by UC.3.5.

**System requirements.** Input: accept start and destination places, route data and the Commuter's choice. Output: place and route requests, the mode comparison, and the trip result with progress and new badges. Interface: HTTPS request to and structured response from the Route Service, mirroring 3.2.3 and 3.2.4 for Open-Meteo. Functional: compare travel modes, confirm completed trips, evaluate achievements, track campus progress. System-wide: limit data sent to the Route Service to the entered places; label route-based figures as estimates and disclose their source.

**External system and flow.** X.6 Route Service, two conduits (Route request, Route response), six input/outputs, and use case UC.3 Plan and Choose a Trip:

| Step | Action | Performer | Code |
|---|---|---|---|
| UC.3.1 | Open Trip Planner | X.1 | the Plan page (not tagged: actor action) |
| UC.3.2 | Enter Start and Destination | X.1 | the Plan form (actor action) |
| UC.3.3 | Request Routes | C.3 | `route_adapter.geocode`, `get_route_options` |
| UC.3.4 | Return Routes | X.6 | the external service (labelled fallback in C.3 when it fails) |
| UC.3.5 | Compare Modes and Recommend | C.2, C.4 | `compare_modes`, `recommend_mode`, `plan_commute`, `explain_recommendation` |
| UC.3.6 | Present Comparison | C.1 | `web_app.render_plan` |

| UC.3.11 | Review Progress | X.1 | actor action |

`tests/test_model_linkage.py` reads the model and checks that every UC.3 action performed by a component has `@realizes`-tagged code and that no other UC.3 ID is tagged.

`UC.3.10` reads stored trips and receives no flow: a flow from UC.3.8 made Innoslate report "prior action is dependent on the later action" (see Intelligence below).

**Risks.** TR.10 Confirmed trips keep start and destination labels (finer than the coarse location 2.5.1 and 3.4.5.2 require); TR.11 Route Service outage, quota or host change; TR.12 Tree conversion is an unsourced assumption.

## Intelligence on import (2026-10-27)

The first import of 10.9 gave a pass rate of 77% with two kinds of error, both in UC.3. Both are fixed in the file now in this folder, and its re-import gave **81% with no errors** (the same rate as model 10.6), leaving warnings only:

- "Prior action is dependent on the later action" (UC.3): UC.3.10 received a flow generated by UC.3.8, and plain string order puts UC.3.10 before UC.3.8. UC.3.10 now receives no flow.
- "Actions that do not satisfy/verify/trace to any requirement" (UC.3, UC.3.1, UC.3.11): UC.3 now satisfies 2.1.11 and 2.1.12, UC.3.1 satisfies 2.1.11, and UC.3.11 satisfies 2.1.13 and 2.2.5.

The warnings that remain are the kinds 10.8 already had (functions F.x not performed by an asset, OP.x without parent or child, requirements satisfied by more than one input/output); the lists for the first three are identical in 10.8 and 10.9. UC.3.1, UC.3.2, UC.3.7, UC.3.10 and UC.3.11 add to "actions that receive no input/output", a warning 16 existing actions already trigger.

## Not done, and not claimed

- **Intelligence is not the whole check.** It found no errors in the corrected file, but its warnings remain and it does not judge whether the requirements are right; the quality flags of the new requirements are still false.
- **The function architecture was not extended.** The new functional requirements 3.3.1.9-3.3.1.12 are allocated to the existing F.2.3, F.2.4, F.2.5 and F.2.6, and the others to F.2, as the existing system requirements are. That allocation is provisional: the Chapter 6 and 7 report still describes eight first-level functions, and whether comparison, achievements and campus progress deserve functions of their own is a team decision.
- **The components were not changed.** The route adapter lives in C.3 and the badge and campus rules in C.2 (ADR 0003, ADR 0005); no new component was added.
- **The Chapter 4-5 and Chapter 6-7 reports were not updated.** They describe 10.7 and 10.8.
- **Numbers are proposals.** The 80% target, the two-trips-per-day and 50 km limits and the 22 kg per tree are project assumptions; the 22 kg has no cited source.
- **Open conflict.** Confirmed trips keep the start and destination labels (TR.10); the team must decide what location detail is stored before any real pilot data is collected.
