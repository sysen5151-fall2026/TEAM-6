About the project

EcoCommute is built as a systems-engineering project: needs, requirements, a function and architecture model in Innoslate, and code that traces back to both. This page is for reviewers and anyone who wants to see how it is put together.

← Back to the productGitHub repository ↗
System of interest

Four internal components, a handful of outside services.

C.0 EcoCommute contains the web front end, the application service, the data adapter and the explanation model. The commuter and the outside services are external: the software controls its response, not people’s travel or the forecast.

Included

Plan and compare, feasibility and recommendation, TCAT direct rides, carpool, confirmed-trip history, badges, campus tree, invite-only accounts, data export and account deletion.

Excluded on purpose

Native apps, passive GPS tracking, carbon credits, live bus positions and multi-leg transit routing. Each would need new interfaces and review.

Privacy by design

Manual entry, no tracking. Your location stays in the browser until you press “Start from my location”. Passwords are salted scrypt hashes, and each account sees only its own trips.

Model ↔ product

Trace any behavior back to a stakeholder need.

Stakeholder → need → requirement → modeled action → code → test. A test reads the use-case actions from the exported Innoslate model and checks that every action a component performs has tagged code and that no other action is tagged.

Not yet

Reviewed emission factors, a language-model explanation, live bus positions, multi-leg transit, and the pilot usability measurements (such as the 30-second entry target).

Estimates, not claims

Every saving is labelled an estimate. Emission factors, the tree goal and all feasibility limits are placeholders or project assumptions until the method reviewer supplies sources.

Provenance

GenAI-assisted work is logged in the prompt log, and code is constrained by the requirement text in SPEC.md. Decisions are recorded in ADR 0001–0009.
